# 2. Практики по этапам жизненного цикла

Здесь — конкретика по каждому этапу SDLC: что поручать агенту, где ставить человека, какие артефакты и петли обратной связи нужны. Примеры даны под закрытый контур (локальные модели через vLLM, MCP к внутренним системам). Модели под каждую роль — в [документе 3](03-agent-roles-and-models.md).

Сквозной принцип: **каждому этапу — свой артефакт на входе и проверяемый результат на выходе.** Агент работает между ними, человек контролирует переходы.

---

## 2.1. Планирование и требования

**Что поручать агенту.** Декомпозиция задачи, черновик спецификации (требования → дизайн → задачи), поиск связанных задач и кода, оценка влияния изменения, draft acceptance-критериев.

**Где человек.** Утверждение намерения и scope. Спека — это контракт, по которому агент потом пишет код; ошибка здесь дорого стоит.

**Практика — spec-driven development (SDD).** Спецификация становится главным артефактом, код — производным. Поток: `требования.md → дизайн.md → задачи.md → реализация`.

**Пример потока (на базе MCP к Jira):**

```text
1. Человек: "Нужна пагинация в /users API"
2. planner-агент: читает задачу PROJ-123 (MCP jira_get_issue, L0 чтение),
   находит текущий эндпоинт и слой данных (поиск по репозиторию),
   пишет черновик дизайна: параметры limit/offset, формат ответа, затронутые файлы
3. Человек: правит дизайн, утверждает
4. planner-агент: раскладывает на задачи-подпункты
5. Переход к разработке
```

**Артефакт на выходе:** утверждённая спека с acceptance-критериями.

---

## 2.2. Разработка (написание кода)

**Что поручать агенту.** Реализация по утверждённой спеке в feature-ветке, рефакторинги, миграция API, исправление багов по воспроизведению.

**Уровень автономии:** L2 (auto-with-review) в feature-ветке. Прямой push в защищённые ветки — запрещён (branch permissions).

**Обязательная обвязка до старта:**

- `AGENTS.md` в корне репозитория с конвенциями, стеком, командами сборки/тестов (см. [документ 5](05-context-engineering-and-guardrails.md)).
- Рабочая сборка и тесты, которые агент может запускать сам.
- Линтер/форматтер с автоисправлением.

**Хорошие практики:**

- **Малые диффы.** Одна задача — один PR. Агенты лучше работают и легче ревьюятся на коротких изменениях.
- **Читать перед тем, как писать.** Агент сперва изучает существующий код и повторяет стиль проекта, а не тащит новые библиотеки.
- **Решать именно поставленную задачу.** Без «заодно отрефакторил полмодуля».
- **Проверка после каждого изменения.** Собрать → прогнать тесты → починить, прежде чем отдавать результат.

**Пример цикла coder-агента (L2):**

```text
feature/PROJ-123-pagination
  ├─ агент: читает спеку + AGENTS.md + затронутые файлы
  ├─ агент: пишет изменения в слое запросов, роуте, типах
  ├─ агент: npm run build  → ошибка типов → чинит
  ├─ агент: npm test        → 2 падения → чинит
  ├─ агент: npm run lint    → автоfix
  └─ агент: открывает PR с описанием (что/зачем/как проверено)
Человек + reviewer-агент + CI → ревью → merge (L1)
```

## 2.3. Тестирование

Это один из лучших этапов для раннего пилота: высокая ценность, низкий риск, встроенная петля обратной связи (тест либо проходит, либо нет).

**Что поручать агенту:**

- Генерация модульных тестов на новый/изменённый код.
- Повышение покрытия на «белых пятнах».
- Воспроизведение бага тестом перед его исправлением (red → green).
- Генерация тестовых данных и фикстур (с обезличенными данными — см. безопасность в [документе 5](05-context-engineering-and-guardrails.md)).

**Антипаттерн, который надо активно отлавливать:** агент подгоняет тест под текущее (возможно, неверное) поведение кода или пишет тест, который «всегда зелёный». Контрмеры:

- Mutation testing — проверяет, что тесты реально ловят ошибки.
- Reviewer-агент с явной инструкцией «проверь, что тест может упасть и проверяет намерение, а не реализацию».
- Человек ревьюит тесты на критичных путях.

**Пример:**

```text
Задача: баг — пагинация теряет последнюю страницу
1. tester-агент: пишет падающий тест, воспроизводящий баг (red)
2. coder-агент: чинит код
3. CI: тест зелёный (green), регрессия закрыта
4. Человек: ревью диффа + теста
```

---

## 2.4. Ревью кода

**Модель:** reviewer-агент даёт замечания (L0 — советник), **решение всегда за человеком**. Агент-ревьюер не должен сам одобрять merge.

**Что хорошо ловит агент-ревьюер:** нарушения конвенций, пропущенная обработка ошибок, потенциальные уязвимости (инъекции, небезопасные дефолты), отсутствие тестов, рассинхрон с описанием PR.

**Что оставить человеку:** архитектурные решения, бизнес-логика, компромиссы, которые требуют контекста за пределами репозитория.

**Практика — ревью по смыслу, а не по строкам.** Хороший reviewer-агент реконструирует изменение как связную историю (что меняется в поведении системы), а не комментирует построчно. Это снижает шум и повышает ценность замечаний.

**Защита от «штамповки аппрувов»:** когда агенты пишут код, именно ревью становится узким местом. Чтобы человек не превратился в «кнопку approve», используйте:

- reviewer-агента как первый фильтр (отсекает мелочь),
- обязательный зелёный CI как merge-check,
- человека — только на решениях, требующих суждения.

## 2.5. Деплой и CI/CD

**Градация по средам — это и есть главный механизм безопасности** (тот же принцип test → prod, что в [релизной политике](../release-policy/release-runbook.md)):

| Среда | Автономия агента | Контроль |
|-------|------------------|----------|
| Эфемерное / preview | L3 (автономно в песочнице) | Только CI |
| Test / staging | L2 (авто + ревью пайплайна) | CI + smoke-тесты |
| Production | L1 (строго подтверждение человеком) | HITL + все merge-checks |

**Что поручать агенту:** генерация и правка CI/CD-конфигов, Dockerfile, IaC; разбор упавшей сборки и предложение фикса;

**Жёсткие границы (guardrails):**

- Деплой в прод, миграции БД, смена секретов/прав — только L1 с явным подтверждением.
- Агент не меняет git config, не делает `push --force`, `reset --hard` в общие ветки без явной команды.
- IaC, затрагивающий живые ресурсы, — показать план (`terraform plan`), подтверждение человеком до `apply`.

**Пример автономной петли на эфемерном окружении (L3):**

```text
Задача: обновить зависимости до безопасных версий
1. ops-агент: создаёт ветку, обновляет манифесты (пиннинг точных версий)
2. CI: сборка + тесты на эфемерном окружении
3. агент: читает упавшие тесты → правит → повторяет (часы, без человека)
4. агент: открывает PR с отчётом
5. Человек: ревью → merge → деплой в prod (L1)
```

## 2.6. Документация

Низкий риск, высокая отдача — ещё один идеальный ранний пилот.

**Что поручать агенту:**

- Docstring и комментарии к публичному API.
- README, гайды, ADR (architecture decision records) из обсуждений и диффов.

- Поддержание `AGENTS.md` и `docs/` в актуальном состоянии при изменении кода.
- Диаграммы (Mermaid) из структуры кода.

**Практика — docs как часть Definition of Done.** Хук `PostTaskExec` или шаг CI запускает docs-агента, который проверяет: изменился публичный API → обновлена ли документация. Это держит доки живыми, а не «написанными один раз».

**Важно:** агент пишет на основе кода и обсуждений, но владелец раздела проверяет фактическую точность. Документация с уверенной, но неверной деталью опаснее её отсутствия.

## 2.7. Эксплуатация и инциденты

**Что поручать агенту (L0/L1):** триаж алертов, корреляция логов и метрик, черновик post-mortem, поиск вероятной причины по трейсам, предложение (не применение) фикса.

**Жёстко human-in-the-loop:** любое изменение в проде во время инцидента. Агент — ускоритель диагностики, а не оператор прод-систем.

**Практика — runtime-диагностика в SDD-цикле.** Даже при спек-ориентированной разработке поведение надо проверять в рантайме: трассировать узкие места, ловить баги, которые проявляются только под реальной нагрузкой. Агент помогает собрать и объяснить телеметрию; инженер принимает решения.

---

## 2.8. Сводная таблица «этап → агент → автономия → артефакт»

| Этап | Роль агента | Автономия | Артефакт на выходе | Петля обратной связи |
|------|-------------|-----------|--------------------|----------------------|
| Планирование | planner | L0/L1 | Утверждённая спека | Ревью человеком |
| Разработка | coder | L2 | PR в feature-ветке | Сборка + тесты + lint |
| Тесты | tester | L2 | Тесты (red→green) | CI, mutation testing |
| Ревью | reviewer | L0 | Замечания | Решение человека |
| Деплой test | ops | L2/L3 | Задеплоено в test | CI + smoke |
| Деплой prod | ops | L1 | Релиз | HITL + merge-checks |
| Документация | docs | L2 | Обновлённые доки | Ревью владельца |
| Эксплуатация | ops | L0/L1 | Триаж, post-mortem | Решение дежурного |
