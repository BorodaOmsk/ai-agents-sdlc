# 6. Дорожная карта внедрения, метрики и антипаттерны

Этот документ сводит всё предыдущее в план действий: как внедрять поэтапно, что измерять, каких ошибок избегать и по каким чек-листам проверять готовность.

---

## 6.1. Дорожная карта по фазам

Движение по уровням зрелости из [документа 1](01-maturity-and-operating-model.md): Observer → Experimenter → Integrator → Pioneer. Не перепрыгивать.

### Фаза 0 — Фундамент (до первого агента)

Цель: собрать обвязку, без которой агенты бесполезны.

- [ ] Поднят vLLM с tool calling, модель класса A проходит проверку из [документа 4](04-vllm-infrastructure.md).
- [ ] В целевых репозиториях есть рабочая сборка, тесты, линтер — агент может их запускать.
- [ ] Написан `AGENTS.md` с конвенциями, командами и границами.
- [ ] Настроены права на инструменты (`ask` по умолчанию, `allow` только на чтение).
- [ ] MCP к Jira/Confluence/Bitbucket: отдельные серверы на среду, прод read-only.

### Фаза 1 — Experimenter (2–3 этапа, низкий риск)

Цель: получить опыт и доверие, не рискуя продом.

- [ ] Пилот: **генерация тестов** (L2) + **документация** (L2) + **ревью как советник** (L0).
- [ ] Снимаются базовые метрики (см. ниже) до и после.
- [ ] Ретро через 2–4 недели: что сработало, где агент ошибался.

### Фаза 2 — Integrator (4–5 этапов)

Цель: агенты в основной разработке под крепким CI.

- [ ] **Разработка фич** агентом (L2) в feature-ветках, обязательный CI + ревью.
- [ ] **Деплой в test** через агента/CI (L2/L3 на эфемерных окружениях).
- [ ] Reviewer-агент как merge-check (первый фильтр), человек — решение.
- [ ] Оркестратор раздаёт работу подагентам (planner/coder/tester/reviewer).

### Фаза 3 — Pioneer (≥6 этапов)

Цель: агенты ведут большую часть цикла, человек — на точках контроля.

- [ ] Автономные прогоны в песочнице (L3): массовые рефакторинги, обновления зависимостей.
- [ ] ops-агент в триаже инцидентов (L0/L1).
- [ ] Прод остаётся строго HITL (L1).
- [ ] Полная наблюдаемость и аудит tool calls.

## 6.2. Метрики

Измеряйте две группы: **результат доставки** (не стало ли хуже) и **работу агентов** (окупается ли).

### DORA — не деградировала ли доставка

| Метрика | Что показывает |
|---------|----------------|
| Lead time for changes | От коммита до прода |
| Deployment frequency | Как часто релизим |
| Change failure rate | Доля релизов с инцидентом |
| Time to restore | Скорость восстановления после сбоя |

Главное: при внедрении агентов **change failure rate не должен расти**. Если растёт — обвязка (тесты, ревью, guardrails) слабая, автономию надо снижать.

### Агентные метрики

| Метрика | Что показывает | На что смотреть |
|---------|----------------|-----------------|
| Доля принятых PR от агента | Качество реализации | Низкая → слаба спека или модель |
| Правок после агента (rework rate) | Сколько приходится переделывать | Высокая → узкое место сместилось в ревью зря |
| Время на ревью PR агента | Не превратилось ли ревью в бутылочное горло | Рост → нужен reviewer-агент как фильтр |
| Итераций агента до зелёного CI | Качество петель обратной связи | Много → плохие тесты/контекст |
| Покрытие тестами (прирост) | Польза tester-агента | — |
| Стоимость/латентность на задачу | Нагрузка на vLLM | Через метрики vLLM и трассировку |

> Антиметрика: «строк кода, написанных ИИ». Она поощряет объём, а не ценность, и провоцирует разрастание и переусложнение. Не используйте её как цель.

## 6.3. Антипаттерны (чего избегать)

| Антипаттерн | Чем плох | Правильно |
|-------------|----------|-----------|
| **Автономия сразу по всему SDLC** | Нет обвязки — агент ломает прод | Поэтапно, с низкого риска |
| **Один «супер-агент» на всё** | Дорого, небезопасно, хуже по качеству | Узкие подагенты с минимальными правами |
| **Ревью «штампом»** | Человек жмёт approve не глядя — узкое место не закрыто | reviewer-агент как фильтр + CI + человек на суждениях |
| **Тесты, подогнанные под код** | «Всегда зелёные», не ловят баги | Mutation testing, ревью тестов, red→green |
| **Доверие к «зелёной сборке» как к успеху** | Команда прошла ≠ задача решена | Проверка против намерения задачи |
| **Контекст «свалить всё»** | Переполнение, утонувший сигнал | Context engineering, поиск вместо дампа |
| **Запись без подтверждения** | Необратимые изменения без контроля | `ask` по умолчанию, HITL на опасном |
| **Внешний контент как инструкции** | Prompt injection | Всё внешнее — недоверенные данные |
| **Открытые версии зависимостей** | Отравление цепочки поставок | Пиннинг точных версий, ревью |
| **Метрика «строк от ИИ»** | Поощряет объём, не ценность | DORA + качество, не объём |
| **Прыжки через уровни зрелости** | Обвязка не поспевает за автономией | Расширять охват по мере роста доверия |

## 6.4. Чек-лист готовности репозитория к агентам

Прежде чем пускать агента в репозиторий:

- [ ] Есть `AGENTS.md` с командами сборки/тестов и границами.
- [ ] Сборка и тесты запускаются одной командой и агент их видит.
- [ ] Линтер/форматтер с автоисправлением настроен.
- [ ] CI прогоняет тот же набор проверок на каждое изменение агента.
- [ ] Защищённые ветки закрыты от прямого push (branch permissions).
- [ ] Merge-checks: аппрув + зелёный CI обязательны.
- [ ] Права на инструменты: `ask` по умолчанию, `allow` точечно на чтение.
- [ ] Секреты не лежат в репозитории; `.env` в `.gitignore`.
- [ ] MCP к прод-системам read-only и выключен по умолчанию.

## 6.6. Минимальный жизнеспособный старт (TL;DR)

Если нужно начать завтра:

1. Поднять vLLM с одной моделью класса A и tool calling ([документ 4](04-vllm-infrastructure.md)).
2. Написать `AGENTS.md` в один репозиторий ([документ 5](05-context-engineering-and-guardrails.md)).
3. Включить два пилота низкого риска: генерация тестов + документация (L2) ([документ 2](02-lifecycle-practices.md)).
4. Права: `ask` по умолчанию, запись — только с подтверждением.
5. Снять метрики, провести ретро через 2–4 недели, расширять охват.
