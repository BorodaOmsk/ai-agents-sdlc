# 4. Инфраструктура vLLM для агентов

vLLM — движок инференса, который раздаёт локальные open-weight модели по OpenAI-совместимому API. Для агентов критично не просто «отдавать токены», а надёжно поддерживать **tool calling** и длинный контекст. Этот документ — о том, как поднять vLLM так, чтобы агенты из [документа 3](03-agent-roles-and-models.md) работали стабильно.

> ⚠️ Флаги и имена парсеров зависят от версии vLLM и семейства модели. Примеры ниже — иллюстративные (на базе документации vLLM, см. [`09-sources.md`](09-sources.md)). Зафиксируйте точную версию vLLM и сверьте флаги под свою модель.

---

## 4.1. Почему именно tool calling — главное

Агент без tool calling бесполезен: он не сможет прочитать файл, запустить тест, вызвать MCP. Поэтому первое, что проверяется на инфраструктуре, — что модель **возвращает структурированный вызов инструмента**, а не описывает его текстом.

vLLM поддерживает для поля `tool_choice`: `auto`, `required` (с версии `0.8.3`), `none` и named function calling. Для агентов нужен `auto` — модель сама решает, когда звать инструмент.

---

## 4.2. Базовый запуск с tool calling

Ключевые флаги — `--enable-auto-tool-choice` и `--tool-call-parser` (парсер **обязан** соответствовать семейству модели: у Llama, Qwen, DeepSeek, Mistral — свои форматы вызовов).

```bash
vllm serve <ПУТЬ_ИЛИ_ИМЯ_МОДЕЛИ> \
  --served-model-name <ID_МОДЕЛИ_ДЛЯ_КЛИЕНТА> \
  --enable-auto-tool-choice \
  --tool-call-parser <ПАРСЕР_ПОД_СЕМЕЙСТВО> \
  --chat-template <ПУТЬ_К_ШАБЛОНУ_ЕСЛИ_НУЖЕН> \
  --max-model-len 131072 \
  --api-key <КЛЮЧ> \
  --host 0.0.0.0 --port 8000
```

Пояснения к ключевым параметрам:

| Флаг | Назначение | Замечание |
|------|------------|-----------|
| `--served-model-name` | Идентификатор, под которым модель видна клиенту в `/v1/models` | Должен совпадать с id модели в конфиге агента |
| `--enable-auto-tool-choice` | Включает авто-выбор инструментов | Без него агент не вызовет инструменты |
| `--tool-call-parser` | Парсер формата вызовов под семейство модели | Неверный парсер = вызовы не распознаются |
| `--chat-template` | Шаблон чата, если модель требует специальный | Нужен для части моделей/парсеров |
| `--max-model-len` | Максимальная длина контекста | Должна совпадать с `limit.context` у агента |
| `--api-key` | Включает проверку ключа | Обязательно для vLLM в сети (в отличие от Ollama) |

> Критично: значение `--max-model-len` на сервере должно **совпадать** с настройкой контекста в клиенте-агенте. Рассинхрон даёт либо ошибку превышения длины, либо «потерю» начала диалога моделью.

---

## 4.3. Проверка tool calling (минимальный тест)

Прежде чем подключать агента, проверьте вызов инструмента напрямую через OpenAI-совместимый клиент. Эталонная проверка (по документации vLLM):

```python
from openai import OpenAI
client = OpenAI(base_url="http://<VLLM_HOST>:8000/v1", api_key="<КЛЮЧ>")

tools = [{
  "type": "function",
  "function": {
    "name": "get_weather",
    "description": "Get current weather in a location",
    "parameters": {
      "type": "object",
      "properties": {
        "location": {"type": "string"},
        "unit": {"type": "string", "enum": ["celsius", "fahrenheit"]}
      },
      "required": ["location", "unit"]
    }
  }
}]

resp = client.chat.completions.create(
    model=client.models.list().data[0].id,
    messages=[{"role": "user", "content": "What's the weather in San Francisco?"}],
    tools=tools, tool_choice="auto",
)
print(resp.choices[0].message.tool_calls[0].function)
```

**Ожидаемый результат:** в ответе присутствует `tool_calls` с именем `get_weather` и валидным JSON аргументов. Если модель вернула текст с описанием вызова вместо `tool_calls` — проблема в парсере или chat template (см. диагностику ниже).

## 4.4. Структурированный вывод (guided decoding)

Для ролей, где нужен строго валидный JSON (reviewer с машиночитаемыми замечаниями, planner с планом задач), используйте structured outputs:

- **Named / `required` tool calling** гарантирует *валидно разбираемый* вызов (vLLM принудительно подгоняет вывод под JSON-схему через structured outputs backend). Важная оговорка: гарантируется разбираемость, но **не качество** вызова — поэтому схему стоит продублировать в промпте.
- Первый вызов structured outputs компилирует конечный автомат (FSM) — несколько секунд задержки, дальше кэшируется.

Практика: для детерминированного управления агентом (handoff между подагентами, строгий формат отчёта) комбинируйте guided decoding с низкой температурой.

## 4.5. Профили запуска под роли

Разные роли — разные компромиссы. Не раздавайте всё одной конфигурацией.

| Роль / класс | Приоритет | Ключевые настройки |
|--------------|-----------|--------------------|
| coder / A | Качество + длинный контекст | Большой `--max-model-len`, квантизация весов при нехватке VRAM |
| reviewer, tester, docs / B | Пропускная способность | Умеренный контекст, выше параллелизм запросов |
| completion / C | Минимальная задержка | Маленькая модель, короткий контекст, отдельный процесс/порт, FIM |

Приёмы под ограниченную VRAM:
- **Квантизация весов** (AWQ/GPTQ/FP8) — задаётся при запуске/в формате чекпойнта.
- **Квантизация KV-кэша** — экономит память на длинном контексте.
- `--gpu-memory-utilization` — доля VRAM под движок (осторожно поднимать, если на карте есть другие процессы).
- Тензорный параллелизм (`--tensor-parallel-size`) — разложить большую модель на несколько GPU.

---

## 4.6. Роутинг нескольких моделей

Поскольку ролям нужны разные модели (A/B/C), есть два подхода:

1. **Несколько процессов vLLM**, по одному на модель, на разных портах. Просто, изолированно, легко назвать `served-model-name`. Подходит для старта.
2. **Шлюз-роутер** перед несколькими бэкендами vLLM (единый OpenAI-совместимый endpoint, маршрутизация по полю `model`). Удобно для агентов, которые обращаются к разным ролям через один адрес.

Для закрытого контура с одним-двумя узлами обычно достаточно варианта 1. Роутер оправдан, когда моделей много и нужен единый вход.

```text
IDE / агенты
   │
   ├── :8000  vLLM — модель A (coder, 131072 ctx, tool-call)
   ├── :8001  vLLM — модель B (reviewer/tester/docs)
   └── :8002  vLLM — модель C (completion, FIM)
```

## 4.7. Наблюдаемость и эксплуатация

Агенты генерируют много обращений к LLM; без наблюдаемости вы не поймёте, где узкое место и сколько стоит задача.

- **Метрики vLLM** (Prometheus-endpoint): пропускная способность, задержка (TTFT, TPOT), заполнение KV-кэша, число вытеснений (preemptions). Рост вытеснений = не хватает памяти под параллельные запросы.
- **Трассировка (OpenTelemetry)** на стороне обвязки агента: сколько шагов, какие инструменты, где петли. Это из рекомендованных практик 2026 (deterministic control flow, auditable state, OpenTelemetry tracing).
- **Логи tool calls** — для аудита (что агент пытался сделать) и для безопасности.

## 4.8. Диагностика типовых проблем

| Симптом | Вероятная причина | Что проверить |
|---------|-------------------|---------------|
| Модель описывает вызов текстом, нет `tool_calls` | Неверный `--tool-call-parser` или отсутствует `--enable-auto-tool-choice` | Парсер под семейство модели; флаг включён; chat template поддерживает инструменты |
| Ошибка превышения длины контекста | `--max-model-len` < запрос, или рассинхрон с клиентом | Привести `--max-model-len` и настройку контекста агента к одному числу |
| Модель «забывает» начало диалога | Контекст клиента > реального на сервере | То же — синхронизировать значения |
| OOM при старте | Модель + контекст не влезают в VRAM | Квантизация, меньше `--max-model-len`, tensor-parallel, меньше `--gpu-memory-utilization` |
| Высокая задержка под нагрузкой | Нехватка KV-кэша, вытеснения | Метрики preemptions; снизить параллелизм или контекст; квантизация KV |
| Клиент не находит модель | `--served-model-name` ≠ id в конфиге агента | Сверить с ответом `/v1/models` |
| 401/403 от vLLM | Несовпадение `--api-key` и ключа клиента | Сверить ключ; для vLLM ключ обязателен |
