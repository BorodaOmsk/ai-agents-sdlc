# 3. Роли агентов и подбор локальных моделей

Принцип зрелых agentic-команд: **не один «супер-агент», а набор узких подагентов (subagents)**, каждый со своей ролью, своим системным промптом, своим набором инструментов и прав — и, что важно для закрытого контура, со своей моделью. Оркестратор раздаёт им задачи и собирает результат (handoff-first orchestration).

Это даёт три выгоды:
- **Экономия железа.** Тяжёлую модель держим только там, где она реально нужна (агентное кодирование). Автодополнение и триаж обслуживают маленькие быстрые модели.
- **Безопасность.** У reviewer-агента нет прав на запись; у docs-агента нет доступа к секретам. Минимальные права на роль.
- **Качество.** Специализированный промпт и контекст под задачу работают лучше, чем универсальный.



---

## 3.1. Карта ролей

| Роль | Задача | Инструменты | Права записи | Автономия |
|------|--------|-------------|--------------|-----------|
| **orchestrator** | Декомпозиция, раздача подагентам, сборка результата | субагенты, чтение репо | нет | L1 |
| **planner** | Спека, дизайн, оценка влияния | чтение репо, MCP (Jira/Confluence) read | нет | L0/L1 |
| **coder** | Реализация в feature-ветке | edit, run, test, git (feature) | да (feature-ветка, L2) | L2 |
| **tester** | Генерация и прогон тестов | edit (tests), run, test | да (только тесты) | L2 |
| **reviewer** | Ревью диффа, замечания | чтение диффа и репо | нет | L0 |
| **docs** | Документация, release notes | edit (docs), чтение репо, MCP Confluence | да (docs, L2) | L2 |
| **ops** | CI/CD, деплой, триаж | run (CI), MCP, git | prod — только L1 | L1/L2/L3 |
| **completion** | Автодополнение в IDE (FIM) | — | нет | — |

Минимальные права — ключевой guardrail. Детали прав и MCP — в [документе 5](05-context-engineering-and-guardrails.md).

## 3.2. Классы моделей под роли

Разделите модели на три класса по требованиям к ним.

### Класс A — агентное кодирование (coder, orchestrator, сложный planner)

Самое требовательное. Нужны: сильное tool calling, длинный контекст (навигация по репозиторию), высокий балл на агентных бенчмарках (SWE-bench Verified), приемлемая скорость.

Критерии (все проверяются «да/нет»):
- Поддержка tool calling в chat template модели — обязательно.
- Контекст ≥ 128K токенов (минимум 32K, но для репозитория мало).
- SWE-bench Verified — чем выше, тем лучше; у хороших open-weight моделей 2026 года это ориентировочно 55–72%.
- Помещается в память GPU с нужным контекстом и квантизацией.

Кандидаты (open-weight, по данным поиска за 2026; **проверить**):

| Модель (семейство) | Чем интересна | Лицензия | Статус |
|--------------------|---------------|----------|--------|
| Qwen3-Coder (Instruct, MoE и dense) | Сильный агентный кодер, хорошее tool calling, разные размеры под железо | Apache-2.0 (у части линейки) | проверить |
| DeepSeek V3/V4 (Coder) | Высокий балл на агентном кодировании, открытые веса | MIT (у части релизов) | проверить |
| GLM (кодовые линейки) | Чистая MIT-лицензия у части версий | MIT | проверить |



### Класс B — быстрые вспомогательные задачи (reviewer, tester, docs, planner-light, triage)

Нужны разумное качество и **низкая задержка/высокая пропускная способность** — эти агенты вызываются часто. Длинный контекст важен, экстремальный интеллект — нет.

- Dense-модели ~7B–32B. Хороший баланс «качество/скорость» на одной-двух GPU.
- Для reviewer важно следование инструкциям и структурированный вывод; для tester — знание тест-фреймворков проекта.

### Класс C — автодополнение в IDE (completion)

Отдельный, очень важный для UX класс. Критерии прямо противоположны классу A:
- Малый размер (быстрый отклик, десятки мс).
- Поддержка **FIM (fill-in-the-middle)** — дополнение по коду слева и справа от курсора, а не просто продолжение.
- Чат-интеллект и tool calling не нужны.

Кандидаты: небольшие code-модели с FIM (линейки Qwen Coder малых размеров, Codestral-подобные). **Проверить** поддержку FIM в выбранной сборке.

## 3.3. Привязка ролей к моделям (референсная схема)

Это стартовая раскладка — подгоните под своё железо и результаты пилота.

| Роль | Класс модели | Почему |
|------|--------------|--------|
| orchestrator | A | Нужны планирование и tool calling |
| planner | A (сложный) / B (лёгкий) | Зависит от сложности спек |
| coder | A | Самая требовательная роль |
| tester | B | Частые вызовы, умеренная сложность |
| reviewer | B | Следование инструкциям, скорость |
| docs | B | Генерация текста, длинный контекст |
| ops | A или B | A для сложного разбора CI, B для триажа |
| completion | C | Скорость и FIM |

Не обязательно держать все классы одновременно. Минимальный жизнеспособный набор для пилота: **одна модель класса A** (coder/orchestrator) + **одна класса C** (автодополнение). Класс B можно обслуживать той же моделью A на старте, если железо позволяет.

## 3.4. Подбор под GPU (ориентиры)

Железо диктует выбор. Грубые ориентиры по VRAM (сильно зависят от квантизации — AWQ/GPTQ/FP8 и длины контекста; **проверить замером**):

| VRAM | Что реально тянет | Стратегия |
|------|-------------------|-----------|
| 24 GB (1×) | Dense-кодер ~14–32B в квантизации + умеренный контекст | Один класс A среднего размера ИЛИ B+C |
| 48 GB (1–2×) | Кодер 32B с длинным контекстом или компактный MoE | A + C уверенно, B по остатку |
| 80 GB (1×) / 2×48 | Крупные MoE-кодеры, длинный контекст | A (сильный) + B + C |
| Кластер (несколько узлов) | Топовые open-weight MoE | Полный набор ролей, роутинг по моделям |

Приёмы вместить больше:
- **Квантизация весов** (AWQ/GPTQ/FP8) — кратно экономит VRAM при небольшой потере качества.
- **Квантизация KV-кэша** — экономит память на длинном контексте.
- Для MoE-моделей — активных параметров мало, но все эксперты держатся в памяти; считайте по полному размеру.

Детали запуска, флаги vLLM и расчёт `--max-model-len` под VRAM — в [документе 4](04-vllm-infrastructure.md).

## 3.5. Критерии приёмки модели (чек-лист перед фиксацией)

Прежде чем «прибить» модель к роли, прогоните её по чек-листу (все пункты — «да/нет»):

1. [ ] Chat template модели поддерживает tool calling (для ролей A/B).
2. [ ] Контекст модели ≥ целевого значения роли (coder — ≥128K желательно).
3. [ ] Модель с нужным контекстом и квантизацией помещается в VRAM.
4. [ ] vLLM поднимает модель с корректным `--tool-call-parser` под её семейство, и tool calling реально срабатывает (не текстом).
5. [ ] Модель проходит 3–5 эталонных задач вашего проекта (например, задачи ScriptRunner для Jira-команды) без ручных правок формата вызовов.
6. [ ] Задержка и пропускная способность приемлемы для роли (для completion — отклик в десятки мс).
7. [ ] Лицензия модели допускает ваш сценарий использования.

Пункт 5 — самый важный: синтетические бенчмарки не заменяют проверку на ваших реальных задачах и вашем стеке.
