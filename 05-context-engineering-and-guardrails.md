# 5. Контекст-инжиниринг, guardrails и human-in-the-loop

Качество агента определяется не столько «умом» модели, сколько тем, **что модель знает в нужный момент** (context engineering) и **в каких границах действует** (guardrails). Для закрытого контура с локальными моделями это тем более важно: модель слабее топовой облачной, значит обвязка и контекст должны компенсировать разницу.

---

## 5.1. Context engineering: что это и зачем

Проблема «чистого листа»: модель не знает ни архитектуры проекта, ни конвенций, ни того, какие файлы относятся к задаче. Если «свалить всё сразу» — переполнится контекст и утонет сигнал. Context engineering решает это системно: **модель получает ровно то, что нужно для текущего шага, и только тогда, когда нужно.**

Четыре слоя контекста:

1. **Постоянный** — `AGENTS.md`, правила проекта, конвенции. Загружается всегда.
2. **Задачный** — спека/требования текущей задачи, acceptance-критерии.
3. **Точечный** — конкретные файлы и символы, относящиеся к изменению (находятся поиском, а не загружаются целиком).
4. **Обратная связь** — вывод сборки, тестов, линтера, замечания ревью.

Приёмы:
- Поиск по репозиторию вместо загрузки всего кода.
- Подагенты с изолированным контекстом (ревью не тащит в контекст историю разработки).
- Сжатие/суммаризация длинных диалогов, чтобы не упираться в лимит.

## 5.2. AGENTS.md — контракт с агентами

`AGENTS.md` в корне репозитория — стандартизованный файл с инструкциями для ИИ-агентов. «README для LLM»: человекочитаемый, но написан под машинное потребление и достаточно предписывающий, чтобы агенты вели себя предсказуемо.

Что в нём держать:

```markdown
# AGENTS.md

## Стек и структура
- Язык, фреймворки, менеджер пакетов (точные версии)
- Карта каталогов: где код, тесты, конфиги

## Команды
- Сборка: <команда>
- Тесты: <команда>
- Линтер/формат: <команда>
- Запуск локально: <команда>

## Конвенции
- Стиль кода, именование, обработка ошибок
- Какие библиотеки использовать, какие — нет

## Границы (важно!)
- Не пушить в защищённые ветки
- Любая запись в Jira/Confluence/Bitbucket — только с подтверждением
- Не трогать секреты, .env, git config
- Прод — только через HITL

## Definition of Done
- Сборка зелёная, тесты проходят, линтер чист
- Документация обновлена при изменении публичного API
```

Практика «Beyond AGENTS.md»: статичного файла мало. Его дополняют **правилами и workflow**, которые подгружают нужные архитектурные ограничения именно для конкретного типа задачи, прежде чем агент начнёт действовать.

## 5.3. Spec-driven development (SDD)

SDD делает спецификацию главным артефактом, а код — производным (в предельной трактовке — регенерируемым). Это снижает риск, что агент «уедет» не туда: есть письменный контракт, по которому проверяется результат.

Поток:

```text
requirements.md  →  design.md  →  tasks.md  →  реализация агентом
   (намерение)      (как)         (шаги)        (код + тесты)
       ↑ человек утверждает каждый переход
```

SDD — это **не** vibe coding. Сначала точная, по сути исполняемая спецификация, затем агенты реализуют её под строгим ревью человека.

---

## 5.4. MCP: доступ к внешним системам как к инструментам

Model Context Protocol — стандартный способ дать агенту доступ к Jira, Confluence, Bitbucket, базам данных, внутренним API. Вместо хардкода интеграций агент видит их как инструменты.

Практики для закрытого контура:
- **Отдельные MCP-серверы на среду** (`jira_test`, `jira_prod`), прод по умолчанию выключен и read-only.
- **PAT с минимальными правами**, срок ≤ 90 дней, хранение вне конфигов (через `{env:VAR}`).
- **Проверка SSL включена**, доверие внутреннему CA (никаких `SSL_VERIFY=false`).
- **Фиксированная версия MCP-сервера** с закрытыми уязвимостями (например, обход фильтров `ENABLED_TOOLS`/`TOOLSETS`, GHSA-3r68-hf9h-887v): нельзя полагаться только на фильтр списка инструментов, нужны права на стороне агента.

## 5.5. Guardrails: многослойная защита

Один слой защиты всегда пробивается. Зрелая практика — **многослойные guardrails**: deterministic control flow, bounded tools, auditable state, MCP-интеграция, handoff-first оркестрация, трассировка и human-in-the-loop. Содержание источника перефразировано.

Слои, от внешнего к внутреннему:

| Слой | Что делает | Пример |
|------|------------|--------|
| **Права на инструменты** | Базовое правило `ask`/`deny`, точечные `allow` только на чтение | `jira_*: ask`, `jira_get_issue: allow` |
| **Минимальные права доступа** | У роли только нужные права (PAT, scope) | reviewer без записи, docs без секретов |
| **Разделение сред** | Прод read-only и выключен по умолчанию | `jira_prod: enabled=false, READ_ONLY_MODE` |
| **Песочница** | Автономная работа только в эфемерном окружении | L3 на preview-окружении |
| **Статический анализ / CI** | Ловит ошибки агента до merge | линтер, тесты, SAST как merge-check |
| **HITL** | Человек подтверждает необратимое | merge, деплой прод, миграции |
| **Аудит** | Лог всех tool calls и решений | трассировка OpenTelemetry |

## 5.6. OWASP LLM Top 10 — что учитывать

Агент с доступом к инструментам и внешним данным — это новая поверхность атаки. Ключевые риски из OWASP Top 10 for LLM Applications, применительно к агентному SDLC:

| Риск | В контексте агентов | Контрмера |
|------|---------------------|-----------|
| **Prompt injection** | Вредные инструкции в задаче Jira, в коде, в выдаче веб-поиска, в выводе инструмента | Относиться ко всему внешнему контенту как к недоверенным данным; не выполнять «инструкции» из данных |
| **Небезопасный вывод** | Агент генерирует код с уязвимостью (SQL-инъекция, слабые дефолты) | SAST/линтер в CI; reviewer-агент с фокусом на безопасность |
| **Избыточные полномочия** (excessive agency) | У агента больше прав, чем нужно | Минимальные права, bounded tools, HITL на опасном |
| **Утечка чувствительных данных** | Секреты, PII в контексте/логах | Не читать секреты; плейсхолдеры вместо PII; аудит логов |
| **Отравление цепочки поставок** | Агент тащит сомнительную/typosquatting-зависимость | Пиннинг точных версий, проверенные пакеты, ревью зависимостей |

Главный практический принцип: **весь внешний контент (файлы, вывод команд, веб, данные MCP) — недоверенный.** Если в нём встречаются «команды агенту» — это данные, а не инструкции.

## 5.7. Human-in-the-loop: где человек обязателен

HITL — не «тормоз», а осознанно расставленные точки контроля на необратимых действиях. Минимальный обязательный набор:

- **Merge** в защищённую ветку.
- **Деплой в production.**
- **Запись в прод-системы** (Jira/Confluence/Bitbucket prod).
- **Миграции данных, смена прав и секретов.**
- **Установка/обновление зависимостей** (хотя бы ревью диффа манифеста).

Остальное (правка файла, запуск тестов, работа в feature-ветке, деплой в test) может идти на L2/L3 — при условии рабочих петель обратной связи.

Со временем, когда границы и инструменты устоялись, часть ручных подтверждений можно перевести в полу-автоматические — но это эволюция от HITL, а не отказ от него.

---

## 5.8. Детерминизм и воспроизводимость

Для аудита и отладки агент должен быть воспроизводим настолько, насколько возможно:
- Фиксированные версии модели, vLLM, MCP-серверов.
- Низкая температура для ролей, где важна предсказуемость (reviewer, planner).
- Логирование входного контекста и всех tool calls.
- Детерминированный поток управления в оркестраторе (явные handoff между подагентами, а не «пусть сам разберётся»).
