# 1. Уровни зрелости и операционная модель

Прежде чем раздавать агентам задачи, нужно честно определить, где команда находится сейчас и куда движется. Внедрение «сразу автономно по всему SDLC» — главная причина провалов. Мировой опыт говорит: расширять охват этапов нужно постепенно, по мере того как крепнет обвязка (harness) и доверие к результату.

## 1.1. Уровни зрелости (сколько этапов SDLC охвачено)

PwC в обзоре 2026 года предлагает делить команды по числу этапов SDLC, где реально используется GenAI. Удобная шкала (адаптировано):

| Уровень | Охват этапов | Что это на практике |
|---------|--------------|---------------------|
| **Observer** | ≤ 1 этап | Автодополнение и чат в IDE. Агентов как таковых нет |
| **Experimenter** | 2–3 этапа | Агенты пишут тесты, черновики доков, объясняют код. Всё под плотным контролем |
| **Integrator** | 4–5 этапов | Агенты участвуют в разработке, тестах, ревью, деплое. Есть обвязка и метрики |
| **Pioneer** | ≥ 6 этапов | Агенты ведут большую часть цикла: план → код → тест → ревью → деплой → эксплуатация. Человек задаёт намерение и проверяет на ключевых точках |



Практический вывод: **не прыгайте через уровни.** Нельзя перейти к автономному деплою, если ещё нет надёжных тестов и статического анализа, которые ловят ошибки агента. Каждый следующий уровень требует более крепкой обвязки.

## 1.2. От AI-assisted к agentic

Важно различать два режима — это разные операционные модели, а не «больше/меньше ИИ».

| | AI-assisted (ассистент) | Agentic (агент) |
|---|-------------------------|-----------------|
| Кто ведёт работу | Человек на каждом шаге | Агент внутри границ |
| Роль ИИ | Автодополнение, подсказки, чат | Планирует, пишет во многих файлах, запускает тесты, открывает PR |
| Роль человека | Пишет и правит код | Задаёт намерение, проверяет на точках контроля |
| Единица работы | Строка / функция | Задача целиком |
| Узкое место | Написание кода | Ревью и проверка результата |

Agentic SDLC — это когда небольшие, узко сфокусированные агенты берут задачу целиком (сгенерировать тесты, открыть PR, собрать release notes, набросать спеку) **внутри доверенных границ**, а не когда один «супер-ИИ» делает всё.

## 1.3. Уровни автономии (главный регулятор риска)

Автономию агента задают не абстрактно, а по каждому инструменту и этапу. Четыре практических уровня:

| Уровень | Поведение агента | Где уместно |
|---------|------------------|-------------|
| **L0 — Suggest** | Только предлагает (diff, текст), ничего не меняет | Любой новый этап, прод-репозитории на старте |
| **L1 — Ask** | Выполняет действие только после явного подтверждения человеком | Запись в Jira/Confluence/Bitbucket, git push, миграции |
| **L2 — Auto-with-review** | Делает сам, но результат обязательно проходит ревью (человек или reviewer-агент + CI) до merge | Разработка в feature-ветке, генерация тестов |
| **L3 — Autonomous-in-sandbox** | Работает автономно долго (часы) в изолированной песочнице, итерирует по CI | Массовые рефакторинги, обновления зависимостей, прогон на эфемерном окружении |

Правило: **уровень автономии = f(обратимость действия, радиус поражения, стоимость ошибки).**

- Обратимое, локальное, дешёвое (запуск линтера, правка одного файла) → можно L2/L3.
- Необратимое, широкий радиус, дорогое (деплой в прод, удаление данных, смена прав) → строго L0/L1 с подтверждением.



## 1.4. Операционная модель: кто за что отвечает

Внедряя агентов, перераспределите ответственность явно. Иначе возникает «ничья земля», где за ошибку агента не отвечает никто.

```
Намерение и приоритеты      → человек (техлид/владелец продукта)
Декомпозиция задачи          → planner-агент, утверждает человек
Реализация                   → coder-агент (L2), feature-ветка
Тесты                        → tester-агент (L2) + обязательный CI
Ревью                        → reviewer-агент (совет) + человек (решение)
Merge в защищённую ветку     → человек (L1, HITL)
Деплой в test                → агент/CI (L2/L3)
Деплой в prod                → человек (L1, HITL)
Эксплуатация/инциденты       → ops-агент (триаж, L0/L1) + дежурный инженер
Документация                 → docs-агент (L2) + владелец раздела
```

Ключевой сдвиг роли инженера: от «написать код» к **«спроектировать среду, задать намерение, построить петли обратной связи»** (harness engineering). Чем лучше обвязка, тем надёжнее работают даже средние по силе локальные модели — а это критично в закрытом контуре, где нельзя взять топовую облачную модель.

## 1.5. Петли обратной связи — сердце системы

Агент хорош ровно настолько, насколько быстрая и честная у него обратная связь. Без неё он «галлюцинирует успех». Минимальный набор петель, которые надо выстроить до запуска агентов:

1. **Компиляция/сборка** — агент видит ошибки сборки и чинит их сам.
2. **Тесты** — красный тест = сигнал агенту итерировать; зелёный = фактическое подтверждение.
3. **Линтеры и статический анализ** — стиль, типы, уязвимости, code smells.
4. **CI** — тот же набор проверок, что у человека, запускается на каждом изменении агента.
5. **Ревью** — reviewer-агент даёт замечания, человек выносит решение.

> Принцип: «зелёная сборка — это ещё не успех». Агент должен проверять результат против **намерения задачи**, а не против «команда завершилась без ошибки». Этот же принцип закладывается в инструкции самим агентам (см. [документ 5](05-context-engineering-and-guardrails.md)).

## 1.6. Как выбрать стартовую точку

Матрица «ценность × риск» для выбора первого пилота:

| Этап | Ценность | Риск | Рекомендация для старта |
|------|----------|------|-------------------------|
| Документация | Средняя | Низкий | Отличный первый пилот (L2) |
| Генерация тестов | Высокая | Низкий | Отличный первый пилот (L2) |
| Разработка фич | Высокая | Средний | Второй шаг (L2 + CI + ревью) |
| Ревью (как советник) | Высокая | Низкий | Хороший ранний пилот (L0) |
| Деплой в test | Средняя | Средний | После стабильного CI (L2) |
| Деплой в prod | Высокая | Высокий | Поздно, строго L1/HITL |
| Миграции данных | Высокая | Очень высокий | Поздно, строго L0/L1 |

Начинайте там, где риск низкий, а петля обратной связи уже есть (тесты, документация). Это даёт команде опыт и доверие, не рискуя продом.
